# 数据库压缩 · 阶段 3：块表 + `input` 列去重（真机回执）

> 阶段 3 交付 `models/block.go`（块表存储层）与 `models/body.go`（`input` 列接入），
> 并在一份**生产库副本**上跑通了完整写读闭环。下面的数字全部出自
> `models/body_real_test.go` 的 `go test ./models/ -run TestChatIOInput_RealDatabase -v`，
> 源库全程只读，耗时 **72.45 s**。

## 一、真机回执

语料：生产库副本的 `chat_ios.input`，**12,483 行 / 5.64 GiB**。

### 1.1 正确性（这一条不过，别的都不用看）

**全部 12,483 行逐字节还原一致。** 每一行都走一遍生产写路径
（`BeforeCreate` → 分块 → 块表 → 引用帧），再走一遍生产读路径
（`AfterFind` → 按引用还原），与源库的原字节比对。

而且每一行的 `typeof` 都与形态一一对上——这条不是形式主义：帧是按 BLOB 落进
`TEXT` 亲和列的，**亲和性一旦把帧转成 TEXT，帧就永久损坏**，而上面那次
逐字节比对照过（它读的是模型层解出来的明文，不是列里的字节）。

| 形态 | 行数 | 说明 |
|---|---:|---|
| 块表（引用帧） | 11,946 | 共 1,156,874 条引用，平均 **96.8 块/行** |
| 逐行帧 | 522 | body < 4 KiB，分不出块来 |
| 存明文 | 15 | 帧比明文还大，按规则 1 退回明文 |
| 空 | 0 | |

### 1.2 容量

| 量 | 值 |
|---|---|
| 唯一块 | 32,993 个 / **191.12 MiB**，平均 5.93 KiB |
| 组 | 11,725 个，平均一组 **7.70 KiB** |

**口径 A**（唯一内容，未压、未计引用）：5.64 GiB → 191.12 MiB（**30.23x**）。

**口径 B**（真正落库）：

| 项 | 字节 |
|---|---:|
| `input` 列（引用帧 / 逐行帧） | 3.37 MiB |
| 块组帧 | 88.21 MiB |
| 块表行（`rpBlockRowBytes=40` 估算） | 1.26 MiB |
| **合计** | **92.84 MiB** |
| **input 列压缩比** | **62.23x** |

### 1.3 写入与读取代价

- **写入 3.79 ms/行**（47.25 s / 12,483 行）：含分块、块表查插、行插入。
  其中分块与摘要本身只占 **1.18 ms**（阶段 0 实测），**其余约 2.6 ms 是块表的
  SQL** ——每次 `Put` 要发 1 次摘要查表 + 新块的组/块两次插入 + 1 次回查，
  且每次 `Create` 一个独立事务（与线上一个请求一次写入同形）。
- **读回 0.70 ms/行**（8.69 s）。**这个数不能当成随机读的性能**：它是刚写完
  就顺着读回来，组缓存是热的、页缓存也是热的。随机访问的性能以阶段 0 为准
  （256 KiB 档无缓存 P95 **22.6 ms**，开 32 MiB 缓存 17.1 ms）。

### 1.4 陷阱 A 的真行复验

从 12,483 行里抽 20 行**真块表行**，照抄 `service/chat.go:314` 的写法只带输出列更新：

- `input` 的**原始列字节**一个字节没变；
- 还原出来的请求体也没变；
- 块表行数没长。

## 二、最重要的发现：线上组只有 7.70 KiB，压实能再省 35.9%

阶段 3 原本把「线上新写的组偏小」列为"已知代价、由阶段 6 的压实兜底"。
真机量出来，**这个代价比预想的大得多，压实不是可选项**：

| | 组数 | 组帧字节 |
|---|---:|---:|
| 线上写入（每次 `Put` 各封各的组） | 11,725 | **88.21 MiB** |
| 同一批内容按 256 KiB 重打 | 777 | **56.53 MiB** |
| 差 | | **再省 31.68 MiB（-35.9%）** |

换成口径 B：**光靠线上写入是 62.23x；压实之后是 61.16 MiB / ~94.4x**
（3.37 + 56.53 + 1.26）。阶段 0 用理想打包算出的 60.89 MiB / 94.9x 由此在
**真机写读闭环**上复现了——两条路互为独立验证。

**为什么线上组这么小**：一个请求一轮对话只新增十几 KiB 的块（其余全是重复的
历史），而每次 `Put` 就只封这一批。7.70 KiB 远低于 flate 的 32 KiB 窗口，
所以线上组基本吃不到长程匹配。

**这不是能靠调参解决的**：想在线攒大组，就必须让组先于行落库，那就等于放弃
INV-1（行与块同事务）。**7.70 KiB 是 INV-1 的直接后果。** 出路只有事后压实，
所以阶段 6 的 `CompactGroups` 从"优化"变成了"必需"。

## 三、只有走真机才抓得到的三个 bug

三个都是**能静默损坏数据**的那一类，且三个都在存储层的单测里看不见。

### 3.1 GORM 的 statement 被钩子污染

钩子拿到的 `tx` 是"正在插入 `chat_ios`"的那个 statement，它的 `Table` 已经被
外层钉成 `chat_ios` 了。而 GORM 的 `Statement.Parse` 是：

```go
if stmt.Schema, err = schema.Parse(...); err == nil && stmt.Table == "" { stmt.Table = ... }
```

`Table` 非空时它就**不推表名**。于是钩子里 `Model(&Block{})` 生成的是
`SELECT * FROM chat_ios WHERE digest IN (...)`，报 `no such column: digest`。

**这个 bug 只有真正的钩子路径上才会出现**——直接拿一个干净的 `*gorm.DB`
调用存储层是看不出来的（`Table` 恰好是空的）。修法：块表的每次查询都先过
`freshDB(tx, ctx)` = `tx.WithContext(ctx).Session(&gorm.Session{NewDB: true})`
（只换 statement，`ConnPool` 与 `Context` 照旧，所以 INV-1 与"事务里读得到
自己未提交的数据"都还在）。

### 3.2 组缓存跨库串味（症状最阴的一个）

组缓存只按**组 id** 索引，而组 id 只在单个库文件内有意义。每个测试新建一个库，
组 id 从 1 重新开始——于是缓存里**上一个库的第 1 组**被当成新库的第 1 组返回。
症状是"**长度对得上、内容全错**"，而且**不报任何错**。

修法：`BlockStore.Reset()`，并在 `models.Init` 里紧跟着 `DB = db` 调用。
生产上库不会中途换，但它同时服务两件事：进程启动（可能是从备份恢复的库，
rowid 回退了）与将来重建存储层那一步（组会被重新编号）。

### 3.3 `length()` 数的是字符，不是字节

写这份真机测试时踩到的：`SELECT sum(length(input))` 得到 **5.18 GiB**，
而阶段 0 在 Go 里累加 `len(in)` 得到 **5.64 GiB**——差 8%。原因是 SQLite 的
`length(X)` 对 TEXT 返回**字符数**（UTF-8 码点），对 BLOB 才返回字节数。
这一列的 JSON 里混着中文与 emoji，于是两个数不等。

后果不轻：所有口径都以字节为分母，用字符数会把压缩比**系统性低估 8%**，
而且会让我自己写的 `checkByte != srcBytes` 守卫失败。修法：一律
`length(CAST(input AS BLOB))`。

### 3.4 还有一个（这条是单测抓到的，一并记下）

`Get` 一度把组缓存当成**传输通道**——解压出来的组只放进缓存，再从缓存取回。
于是 `cacheBytes<=0`（关缓存）时读路径整个失效，报"组 1 不在缓存里（刚取过？）"。
修法：每次调用自己有一个 `resolved` map 兜住数据，缓存降级为纯粹的"省一次解压"。
**缓存本来就该是可选的**——把正确性挂在它身上，等于关掉缓存就关掉读路径。

## 四、设计上被真机确认 / 修正的几条

1. **钩子必须是 `BeforeCreate`，不是 `BeforeSave`。** 写路径的第二半是
   `Updates(ChatIO{OutputUnion: ...})`；`BeforeSave` 在这里也会触发，而钩子拿到的
   `Input` 是零值。GORM 的 `Updates(struct)` 靠零值跳过恰好挡住了这一下，
   **但那是实现细节，不该拿来做数据安全的前提**。`BeforeCreate` 只在插入时触发，
   这一类问题从定义上就不存在。
2. **`BodyBytes`（具名 `[]byte` + `driver.Valuer`）是"让内容决定存储类"的正确做法**：
   明文写 TEXT、帧写 BLOB。受益的是 `typeof(input)` 这条可审计的不变量——
   迁移时一句 `WHERE typeof(input)='text'` 就能挑出还没迁的行，而 `typeof`
   只读记录的类型头、不读载荷。丢掉它就只能把每行载荷的前几字节都读出来比对。
3. **块表只服务 `input` 一列**（阶段 0 定的）。`of_string` / `of_string_array`
   继续走序列化器，读路径完全不受块表影响。
4. **`BlockChunkAvg` 一旦有数据落库就不能改**：改了切点全错位，块表当场作废。
   这一句写在常数旁边。

## 五、诚实的边界

- **这是一次全量重写，不是原地迁移。** 测试把 12,483 行**重新写进一个新库**，
  量的是"生产写路径本身对不对、代价多大"。**历史行的原地迁移还没做**（阶段 4），
  所以"迁完之后体积真的变小"这件事**还没有被验证过**。
- **读回的 0.70 ms/行是热缓存下的顺序读**，不是随机读。随机读以阶段 0 为准。
- **写入 3.79 ms/行是在这份语料、这个块表规模（33k 块）上量的。** 块表的
  摘要查表走唯一索引，随规模是对数增长；但插入时的组/块两次 INSERT 与回查
  是固定的 3–4 条语句，这部分不随规模改善。
- **`rpBlockRowBytes = 40` 是估算**，沿用阶段 0 的常数。它翻一倍也只多 1.26 MiB。
- **压实能省 35.9% 是"重打一遍"算出来的上界**，不是真跑了压实。真实压实还要
  面对"旧组何时能删"（引用它的行要全部改完才能回收），实际收益会低于这个上界。
- **这次没跑 `-race`**：真机测试量的是写读闭环与容量，不是并发正确性。
  并发正确性由 `models/block_test.go` 的 `GroupCache_StableUnderConcurrency`
  与全仓 `-race` 覆盖。
- 语料里 **522 行走了逐行帧、15 行存了明文**，所以唯一块数（32,993）比阶段 0
  的（33,588）略少——阶段 0 把**所有**行都送进了分块器。两个数不能直接相减。
