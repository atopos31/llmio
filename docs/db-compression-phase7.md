# 数据库压缩 · 阶段 7：空间回收的自动推进，与整库重整（真机回执）

## 〇、一句话结论

**把库压到 155 MiB 之后，那 6.2 GiB 的空洞在原界面上没有对症的按钮。** 唯一的
「空间回收」按实测要跑七个多小时，而且每一批都在跟聊天请求抢写锁。这一阶段补上另一半
——**整库重整（VACUUM）**：同一份 7.05 GiB 的库，**7.0 秒**收干净（6.28 GiB → 783.79 MiB）。

代价是那 7 秒里读写都进不来：实测窗口内 24 发聊天请求，**3 发直接 500**
（`database is locked (5) (SQLITE_BUSY)`，等满 5.164 秒才放弃）。

顺带修掉两处**只有真机能发现**的东西：

1. 定死的批量。512 条语句在一份库上是 1.1 秒，在另一份形态更散的库上是 **8.9 秒**——
   越过写请求 5 秒的耐心，成片 500。
2. 重整期间状态接口整片 500。用户点完「立即重整」，卡片立刻变成一片报错，
   连"正在重整"都看不到。

---

## 一、两条路的分工

它们不是替代关系，是分工。同一份 7.06 GiB 的库：

| | 整库重整（VACUUM） | 增量回收 |
|---|---|---|
| 耗时 | **7.0 秒**（本轮，6.28 GiB 是空闲页）／**56 秒**（阶段 5，7.06 GiB 全是活页） | 881 秒（十轮） |
| 额外磁盘 | 2× 库大小 + 64 MiB | 不要 |
| 窗口 | 全程 EXCLUSIVE，**读写都进不来** | 每批一把写锁，读不受影响 |
| 写请求 | 等满 5 秒耐心即失败 | 持续模式下一批一批地让路 |
| 中途停止 | **不行**（一条语句，没有"批间"） | 可以（批间生效） |
| 适合 | 迁移、回滚、批量删除之后的**大空洞** | 小的、经常性的那部分 |

原先只有右边那一半。用户把 7 GiB 压到 155 MiB 之后，面对 6.2 GB 的空洞，控制台上唯一
能点的是"慢慢收"——而那条路的页/秒是 57 起（固定开销占大头），要跑七个多小时，且每一批
都在抢写锁。

## 二、增量回收：批量必须跟着库走

### 2.1 那个旋钮不在参数上

`PRAGMA incremental_vacuum(N)` 的 `N` 被**生产驱动（glebarez/sqlite）忽略**：`(1)`、
`(4096)`、无参形态都**恰好放掉一页**（N∈{1,2,16,64,1024,4096} 逐一验过）。同一份文件换
`modernc.org/sqlite` 直连则一次放约 4,093 页——**差别在驱动，不在 GORM**。

所以"每次 N 页"这个旋钮在生产上不存在，能旋的是**一个事务里连打多少次**：逐次调用的固定
开销（建 journal／落盘／删 journal）与"搬了几页"无关，合进一个事务就把它摊到 K 页上。
探针实测（7.06 GiB／freelist 1.37M 页）：

| 每事务 | 单事务耗时 | 页/秒 |
|---|---|---|
| 256 | 2.0 s | ~128 |
| **512** | **1.1–1.3 s** | **~430** |
| 2048 | 3.3–4.2 s | ~560 |
| 16384 | 31–34 s | ~500 |

### 2.2 「512」被真机推翻

上表的前提是"512 条 ≈ 1.1 秒，翻四倍也还在 `busy_timeout` 以内"。那个数只对当时那份库
成立：换一份 freelist 1.83M 页、形态更散的库，**同样 512 条要 8.9 秒**（111 轮／1000 秒
真机回执），直接越过 5 秒耐心——那个窗口里 11 条聊天请求有 **6 条** `SQLITE_BUSY` 500，
活下来的 5 条也都花了 3.9–5.9 秒。

两份库同样是 512 条，差 8 倍。**没有任何一个常数能同时适配两者**，所以批量不再定死，按
上一批的实测耗时外推（`nextBatchSize`）：

- **阻尼不对称：缩得快、涨得慢。** 缩是止损（这批已经握久了），一次允许减半；涨是试探，
  一次只涨 1.5 倍——试探过了头的代价（一批握满写锁、打死写请求）比试探不足大得多。
  慢库上 64 → 96 → 144 就稳住了。
- **没打满的批次不参与调整**：freelist 快空时这批短，是因为活少而不是"效率高"，
  拿它外推会把下一趟的开头推成一个大得离谱的批。
- 起点 64（**每趟重置**，不复用上一趟的终值）：第一批无从预知库有多慢，而它照样要付代价
  ——512 在慢库上第一批就是 8.9 秒。边界 16–512，目标每批 2.5 秒（`busy_timeout` 的一半）。

### 2.3 持续模式：一条对写请求的硬保证

持续模式下一轮恒等于**一批**，批与批之间松手 100 ms。合起来：

```
写请求的耐心是 busy_timeout = 5 秒（超了就失败）。
一批的目标耗时是 2.5 秒，
所以任何一把写锁最多被握两秒半左右 —— 写请求等得过。
```

这条保证原先挂在"一批 512 条标称 1.1 秒"上，而那个数只对当时那份库成立。现在它不挂在
"某个常数够小"上，而挂在**按实测耗时自我调整的批量**上——那是它唯一能成立的形式，因为
"一批要多久"随库的形态走，事先算不出来。

100 ms 而不是 1 秒：窗口要长到等待中的写请求能撞进来（SQLite 的 busy handler 是递增睡眠
重试，1/2/5/…/100 ms），但不必长到"一撞就中"。真机那一趟放 2,628 批，每批歇 1 秒就是
44 分钟的纯等待（整趟从 15 分钟变成约 1 小时），100 ms 只要 4–5 分钟。

一趟最后收敛到的批量记进回执的 `batch_size`：它是诊断读数，因为"这台机器上一批能收多少"
直接决定"收完这个洞要几轮"。

## 三、整库重整（VACUUM）的入口

- **磁盘预检在动手之前（同步）**：`2× 库 + 64 MiB`。不够就拒，并把三个数一起回给前端
  （`file_size` / `free_bytes` / `need_bytes`）——磁盘不够时"差多少"比一句"失败"有用得多。
  VACUUM 跑到一半满盘会把库留在说不清的状态，而这是唯一能在动手前知道的事。
- **占位在响应之前落下**（`StartVacuum` 同步做），理由同迁移与回收：接口答的"开始了"
  必须在响应写出去之前就是真的，否则连点两下两个都答成功。
- **回执如实**：`kind=vacuum` / `source=manual` / `stop_reason=vacuumed`。记成 `reclaim`
  会让翻记录的人以为跑的是增量回收。
- **`reclaiming_kind` 是内存量，不能拿回执里的 `Kind` 顶替**：回执写的是**上一次跑完**的
  那趟任务（running 记录要等收工才落库），正在跑的时候它是张冠李戴的旧值。而这两条路在
  界面上是两套说法：重整不能中途停，耗时也差一个数量级。
- **重整停不了**：它是一条语句，没有"批间"这个时机。按下停止按钮会得到一句说清缘由的
  拒绝，而不是与"当前没有回收在跑"混在一起——后者是**误报**，用户明明看着它在跑。

## 四、真机回执

源库 `D:\llmio-test\llmio-repaired.db`（7.05 GiB／12,483 行，`quick_check ok`）。
副本上先按真实成因（日志清理）删掉大部分 `chat_ios` 行把 freelist 造出来，再跑。

跑法：`python e2e/check_vacuum.py --db D:\llmio-test\llmio-repaired.db`
（源库只读打开，一切写入都落在 `--workdir` 下的副本上；另有 `--leave` 备好实例交人手点）

| | 读数 |
|---|---|
| 库 | 7.05 GiB／2,000 行 chat_ios｜freelist **1,647,057 页 = 6.28 GiB** |
| 预检 | 需要 14.16 GiB，可用 232.71 GiB |
| 重整 | **7.0 秒**｜文件 **7.05 GiB → 783.79 MiB**（缩掉 6.28 GiB，111.53 MiB/秒） |
| 回执 | `kind=vacuum source=manual status=done reason=vacuumed freed=6.28 GiB duration_ms=6853` |
| 核对 | 接口自报的 `freed_bytes` 与文件实际缩量**逐字节相等**（drift 0）；重整后 `freelist_count == 0` |
| 期间写请求 | 24 发：**成功 21／失败 3**（500 `SQLITE_BUSY`）｜6 发明显变慢（≥0.5 秒），这一段持续 5.7 秒 |
| 失败那一发 | 等了 **5.164 秒**才放弃 |
| 收工后 | 6 发全 200，最长 0.016 秒（空载基线 0.016 秒） |

那 5.164 秒顺手修掉了界面上一个**没人验证过的数**：`vacuum.step_2` 三语原本写着"最长等待
**60 秒**后放弃"。写请求的耐心就是 `busy_timeout` 的 5 秒，现在三语都改成实测口径。
验收车也加了这一项读数（`worst_failed_seconds`），下次换机器可以直接重量。

### 4.1 验收车的两条设计

1. **判据不预设"一定会失败"。** 窗口里那几发写请求到底是"等满 5 秒然后 500"，还是"排队慢
   一点但都成了"，只能量——所以判据取一个析取：要么有失败，要么最长等待明显盖过空载。
   两个都不成立才说明**窗口是假的**；而一旦量到"全都成了"，那是好消息，但界面上那句
   "写入请求会直接失败"就成了假话，这条红的正是要有人去看一眼那句话。
2. **第 0 步硬碰一次"它用的就是我们复制的那份库"。** 库路径写死为 `./db/llmio.db`、相对
   进程工作目录解析：指错一层不会报错，它会老老实实建一个空库，于是重整"0.0 秒收工、
   文件 152 KiB"——每一条判据都绿，结论全错。这一步已经踩过一次。

## 五、缺口：重整期间状态接口整片 500

### 5.1 现象

在 7 GiB 的副本上点下重整，状态页立刻变成一片报错：

```
GET /api/logs/compression -> 500 "Failed to load compression policy: database is locked (5) (SQLITE_BUSY)"
```

### 5.2 根因

VACUUM 全程持 EXCLUSIVE，那几块状态**一个字都读不出来**。而状态页每 2 秒轮询一次，
于是每一次都等满 `busy_timeout` 才失败（`ReadDBStats` 那条读还会重试 3 次，约 16 秒）
——用户连"正在重整"都看不到，更看不到那句"不能中途停止"的说明。

**而这条路上答案根本不缺**：

- "此刻在干什么"（`running` / `reclaiming` / `reclaiming_kind` / `reclaim_stopping`）
  全在内存里，是 service 那几个原子量，不需要读库；
- "策略与回执"在这几十秒里**一个字都不会变**：它们只在任务收工、或用户在控制台保存时才写。

### 5.3 破法

`handler/log_compress.go` 两条退路，都在读库**之前**：

1. **先手判掉**：`ReclaimingKind() == vacuum` 时直接拿上一次那一份，一次库都不碰
   ——这是"不要去等那 5 秒"的全部意义（用例钉的是耗时 < 1 秒）。
2. **撞锁退回**：其它任务占着锁（迁移的批、回收的批、日志清理）时，读会撞上 BUSY，
   这时同样拿上一次那一份。判据用与重试**同一套** `service.IsBusyErr`（因此把它导出了）
   ——分头写迟早会漂。

退路发出去的那一份，库里那几块**如实标成旧的**（`db.stale = true`），而"此刻"那几个字段
**现算**：整条退路的全部价值就在这四个字段上。

### 5.4 两个前提，都必须写下来

- **策略与回执只在这几个写路径上变**（保存策略、任务收工）。缓存不是"反正会过期"，
  而是"它没变"。旧到什么时候？顶多一趟重整那么久——它一收工，下一次轮询就真读了。
- **换了库就不算数**：缓存是进程级的，而它说的是某一个库文件的属性。这条对生产没影响
  （路径写死），但它是测试之间串味的直接原因——测试里每个用例一份库，症状是"形状都对、
  内容全是另一个库的"。`service/db_stats.go` 的 `dbStatsCache` 同一条规矩，理由是
  `models/block.go` 的组缓存本来就在 Init 时整个丢掉。

### 5.5 用例

- `TestGetCompressionStatus_SurvivesAVacuumHoldingTheLock`：另一条连接 `BEGIN EXCLUSIVE`
  按住整库，`StartVacuum` 把占位落下（占位在返回之前，所以"正在重整"是个能按住的状态，
  不是一次抛硬币），然后断言：状态接口 200、`reclaiming_kind=vacuum`、
  **耗时 < 1 秒**、`db.stale` 为真且 `db.rows` 等于上一次。
  用 `BEGIN EXCLUSIVE` 而不是 `BEGIN IMMEDIATE`：`journal_mode=delete` 下 RESERVED 只挡写，
  读照样进得来，而这里要复现的正是"读也进不来"。
- `TestGetCompressionStatus_ServesLastKnownWhenTheReadHitsBusy`：这是这段测试里唯一一条
  慢用例（**5.18 秒**，要等满一次 `busy_timeout`）。值——真机上"迁移跑着的时候点开始
  迁移会 500"就是这一类。

## 六、界面口径

- **两个按钮，两套代价**：回收说"写请求排队、多半成功"（持续模式还给了 0.1 秒松手的硬
  保证），重整说"读写都进不来、写入直接失败"。这两句话的分量不一样，所以入口也分开点。
- **`auto_vacuum=0` 的库上「回收」是灰的，而且必须给理由**：那种库上
  `PRAGMA incremental_vacuum` 是个 0.000 秒的空操作——按下去不报错、也不缩一个字节，
  比按钮灰着更糟。所以判据是 `auto_vacuum !== 2` 即置灰，理由写成 `no_auto_vacuum`，
  并**指向隔壁那个能办事的按钮**（「立即重整」）。交人自测时第一个问题就是这个
  （"为什么回收一直是暗的"），界面上那句解释必须答得上。
- **定时回收**：默认门槛 256 MiB、周期 1 小时，可关（默认关）。低于门槛，一趟回收省下的
  空间与"占一次写锁、翻一遍整库"的打扰不成比例。手动点不看策略（与迁移、日志清理一致）。
- 文案三语同步改写（`compression.reclaim.*` 与 `compression.vacuum.*` 全部词条），
  包括"实测 7 GiB 的库约 57 秒"这类数字的出处说明。

## 七、诚实的边界

1. **7.0 秒与 56 秒是同一件事的两端。** VACUUM 的耗时跟**活页量**走，不跟文件大小走：
   本轮这份库 6.28 GiB 是空闲页（只需截断，不搬），于是 7 秒；阶段 5 那份是 7.06 GiB
   全是活页（要一页页读+写+记 ptrmap），56 秒。界面上写的"约 57 秒"是**上界**，不是典型值
   ——用户刚删完日志、面对一个大洞时，实际会明显更快。

   交人自测时又量到两个端点，同一天同一份库：先点迁移（762 MiB 明文 → 4.8 MiB），
   再点重整，**7.05 GiB → 30.5 MB，895 毫秒**（放掉 1,839,284 页）——因为此时活页只剩
   几 MiB。紧接着再点一次是 **0 页 / 314 毫秒的空操作**（没有可放的页）。所以
   "同一个按钮，一秒和一分钟都是它"这句话在界面上没法回避，只能把估算写成上界。
2. **写请求那 3 发失败是实测，不是设计意图。** 界面上那句警告由它兜底；但 21 发是成功的，
   所以"彻底不可用"这种说法也过头了——文案写的是"写入请求会直接失败"，指的是那一批发不
   出去，不是"一个字都写不进"。
3. **重整不可停，也没有进度**。它是一条语句，只能等。前端因此不画停止按钮。
4. **状态接口的退路有前提**（5.4）。如果哪天有别的代码路径去写那几条 Config，缓存就会发
   陈旧的一份——那时要么让那条路径也更新缓存，要么把缓存改成"只在这几个函数里失效"。
5. **增量回收的页/秒抖动 ±1.5 倍仍然在。** 自适应批量保证的是**窗口**（写请求等得过），
   不保证吞吐；界面上那个"约几分钟"的估算是按平均值算的。
6. **只在一个驱动（glebarez/sqlite）+ 一份库上量过。** 换驱动或换页大小，数都要重新量
   ——`incremental_vacuum(N)` 参数被忽略这件事本身就是驱动差异。
