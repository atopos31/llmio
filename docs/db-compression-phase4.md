> 重新写进一个**新库**，量的是"生产写路径对不对"。它刻意绕开了"迁完之后库
> 真的变小了吗"，因为那个问题要在原地动过行才算数。阶段 4 就是去动它。

> 整条闭环的真机数字。数字出自 `service/log_compress_real_test.go` 的
> `go test ./service/ -run RealDatabaseMigration -v`，源库全程只读。

## 一、真机回执

语料：生产库副本，**12,483 行 / `input` 列 5.64 GiB / 文件 7.05 GiB**。

### 1.1 正确性

**全部 12,483 行逐字节还原一致。** 迁移完之后每一行都走一遍生产读路径
（`AfterFind` → 按引用还原），与源库的原字节比对，共 5.64 GiB。

而且**回滚又验了一遍**：`RunLogDecompress(full)` 把库里 12,468 行帧全部还原
成明文之后，再次逐行比对，仍然逐字节一致，共 5.64 GiB。

这一遍要说清它验到了什么、没验到什么：迁移与回滚**共用同一套骨架**
（`runCompressMode`，只有"挑哪些行"和"改成什么"不同，见 `service/log_compress.go`
里那段注释），所以它不是一次独立实现意义上的交叉验证。它真正加的东西是两件：
①解码是在**迁移提交之后**、从盘上重新读出来的字节上做的，而不是同一事务里
手里还热着的那份；②明文回写这条路（`rewriteBodies` 传 `BodyBytes` 让内容决定
存储类）走通了——这条路写错的话，列里的格式就错了，而**读路径仍然读得出来**，
于是错会一直躺着。

### 1.2 库真的变小了

| 量 | 值 |
|---|---|
| 迁移耗时 | **36.052s**（扫 12,483 行、改 12,468 行、跳过 15 行） |
| `input` 列 | 5.64 GiB → **3.37 MiB**（1714.76x） |
| 唯一块 | 32,993 个 / 191.12 MiB，平均块 5.93 KiB |
| 组 | 891 个 / 56.87 MiB，平均一组 **219.64 KiB** |
| **口径 B**（真正落库 = 引用帧 + 组 + 块表行） | **61.50 MiB** |
| **input 列压缩比** | **93.95x** |
| VACUUM | **11.129s**，7.05 GiB → **1.46 GiB**（省 5.59 GiB / **79.3%**） |

两个数必须一起报，只报一个都会得出错论：迁移本身把 5.64 GiB 压成 61.50 MiB，
但**在 VACUUM 之前文件一字节都不缩**——`auto_vacuum=0` 时迁移只是把页还进
freelist。只看"迁移后文件多大"会以为白做了；只看"文件小了 79.3%"会以为
迁移顺手就把空间还了，于是在真正的部署里漏掉 VACUUM 这一步。

### 1.3 最重要的发现：迁移打的组是线上逐行写入的 28 倍

| | 平均一组 | 组数 | 组表总字节 |
|---|---:|---:|---:|
| 阶段 3 线上逐行写入 | **7.70 KiB** | 11,725 | 88.21 MiB |
| **阶段 4 迁移（批 64 行）** | **219.64 KiB** | 891 | 56.87 MiB |

同一个块表、同一份唯一内容，**只是换个写入节奏，组表就差 31 MiB（35%）**。
原因很直白：逐行写入时每行结束就把手上那个没攒满的组封帧落库，于是大量组
停在几 KiB；迁移是**批量**打包的，一批 64 行的块一起进分组器，几乎每帧都能
攒到接近 `BlockGroupTarget`。

**填充率 85.8%**，对照阶段 3 离线量出的压实上界（把整库唯一内容按 256 KiB
重打一遍 = 56.53 MiB），现为 56.87 MiB，只多 348.13 KiB（**0.6%**）。

**这条顺带把计划里悬着的 `BatchBytes` 调参问题结案了**：批大小原来是个
纯凭感觉选的值（64 行 / 32 MiB），现在知道调大它换不来多少东西——离线压实
是"不按批、想怎么打就怎么打"的极限成绩，而迁移离极限只有 0.6%。往上调批大小
顶多多拿那 0.6%，代价是峰值内存翻几倍（`PutBatch` 要求整批原文同时在内存里）。
**默认值就是近最优，不要再调。**

## 二、迁移引擎：几个必须这么写的决定

### 2.1 绕开模型，直接操作列

候选行一律**裸 SQL** 取，`UPDATE` 一律裸 SQL 发。两条理由都是"用模型会静默做错事"：

- **用模型读**：`AfterFind` 会先把帧解成明文，于是"这一行迁没迁过"就看不出来了。
  迁移的候选过滤靠的正是"列里现在是什么形态"，一解压这个信息就没了。
- **用模型写**：回滚路径上 `BeforeCreate` 会**把明文再压回去**，回滚跑完等于没跑。

编解码本身仍然委托 `models.PackBodies` / `models.UnpackBody`——与生产钩子
同一份代码，不做第二份实现。

### 2.2 水位与数据同一个事务

中断点只有两种合法结果：整批连水位一起回滚（重启后重跑同一批），或者整批连
水位一起生效（下一批）。**不存在"数据改了、水位没动"**——那个中间态会让同一批
被压第二遍。幂等能兜住结果，但白扫一遍全批候选。

`TestLogCompress_FailedBatchRollsBackWatermark` 钉的就是这条：注入一批失败，
断言水位没动、数据也回滚了。

### 2.3 `typeof` 判形态，不额外加标志列

帧按 BLOB 落进 `TEXT` 亲和列（SQLite 的亲和性只转换 TEXT↔数字，不碰 BLOB），
所以**形态与 `typeof` 一一对应**，不需要任何标志列。

而且 `typeof` **只读记录的类型头、不读载荷**——这一列平均 470 KiB，真去读载荷
的话光是筛选就能把迁移拖垮。状态页的 `pending_rows` 也是这么数的，所以它
便宜到可以在每次读状态时跑一次。

### 2.4 锁序：`maintenanceMu` 必须先于事务

迁移与日志清理共用一把 `maintenanceMu`，而且**两边都必须在开事务之前取锁**。
反过来写（先开事务再取锁）会与另一条路的持锁事务撞成死锁。

取锁的粒度是**每批**，不是整个跑程：一批几十毫秒，中间放手的空档足够日志
清理插进来。清理侧用 `TryLock`，抢不到就跳过本轮而不是排队等
（`TestCleanLogsBusyWhenMigrationHoldsLock`）。

另外，一轮迁移只能有一个，用 `compressInFlight` 这个 CAS 挡——不能复用
`maintenanceMu`，因为锁是每批一取的，挡不住"两个 run 交替取锁"。

### 2.5 不动 `updated_at`

`updated_at` 正是冷静期过滤器的输入。迁移自己把它刷新，就等于把这行重新标记成
"刚被写过"，下一轮又会绕开它（`TestLogCompress_DoesNotTouchUpdatedAt`）。

## 三、迁移与 VACUUM 对在线请求的影响

这一节回答一个运维问题：**跑迁移要不要停服？**

### 3.1 迁移：不需要停，代价是一次 INSERT 等约 90 ms

折算下来一批约 185 ms（36.052s ÷ 12483 行 × 64 行/批，**这是折算不是实测**），
每批持写锁。所以最坏情况下，一个在途请求的日志 `INSERT` 会等一批的时间。
读**不受影响**——SQLite 允许读事务在写事务提交前继续读，而 `busy_timeout=5000`
远大于 185 ms，所以请求不会报错，只是偶尔慢一下。

一个"占用率旋钮"（批间 sleep）是值得的，因为"迁移该跑多凶"是运维判断，
不是技术判断。**但当前没有做**：批大小已经是现成的杠杆，先把批调小就能降占用。

### 3.2 VACUUM：需要停，这是 SQLite 的物理约束而不是设计缺陷

VACUUM 持排他写锁、峰值需要约 2× 库大小的空闲磁盘，实测在 7.05 GiB 的库上
**62.9s**、迁移后的 1.46 GiB 库上 **11.1s**——两个都远超 `busy_timeout=5000`，
在途请求**必然**吃 500。

**所以 VACUUM 不做成接口。** 做成按钮会给人"点一下就能在线回收"的错觉，
而它做不到。它应当是一个**维护窗口步骤**，写在文档里。

阶段 5 的 `auto_vacuum=INCREMENTAL` + 增量回收才是消掉这个离线要求的东西。

### 3.3 一个没有量过的数

**迁移期间请求延迟的 P95 没有实测。** 上面那个"约 90 ms"是从批量耗时与
占用率推的，不是测出来的。要真给这个数，得在迁移跑着的时候并发打请求。

## 四、门的清单

单元/集成（`service/log_compress_test.go`，16 条）钉的是**状态机**：
迁移与幂等的往返、不碰 `updated_at`、冷静期跳新行、水位续跑、失败批回滚水位、
连续失败转 `failed`、拒绝并发跑、批间暂停、暂停在没跑时也持久化、
回滚往返、批内打组、与清理互斥、策略夹取、备份判定、空库非错、空 `input` 不碰。

运维接口（`handler/log_compress_test.go`，7 条）钉的是**几件错了不会报错、
只会静默做错事的事**：

1. **没备份时拒绝开跑。** 迁移原地改写历史行，跑起来不报错、跑完也读得回来，
   所以"该拦没拦"在正常运行中完全看不出来——只在真出事、想把备份盖回去的
   那一刻才暴露。
2. **确认之后如实记成 `forced`。** 存证要记的是**当时的事实**；记成 `manual`
   会让后来翻记录的人以为有备份可退。
3. **回滚的两道门。** `confirm` 不是字面量、或 `full` 不为 true，都必须拒绝：
   从水位续跑会静默漏掉全表前一半的帧，而它跑完是"成功"的。

真机（`service/log_compress_real_test.go`，1 条）钉的是**形态迁移本身**：
整库逐字节往返 + 回滚后再往返 + 容量账 + VACUUM。

## 五、诚实的边界

- **批 185 ms / 请求等 90 ms 是折算的**，不是量出来的。请求 P95 没测（§3.3）。
- **VACUUM 的 62.9s（7 GiB 库）与 11.1s（1.46 GiB 库）都是本机 SSD 上的数**；
  机械盘上不是这个量级，而"要不要停服"的结论只会更保守，不会更松。
- **迁移是分钟级、不是秒级**：36s 对应 12,483 行 / 5.64 GiB。库再大 10 倍就是
  6 分钟量级（块表的摘要查表是对数增长，但插入与回查是固定几条语句，
  这部分不随规模改善）。
- **`TestLogCompress_PacksGroupsInBatches` 钉的是"批内打组"这个行为**，
  不是"批越大组越满"这个量——后者是本次真机量出来的，单测里那份语料太小，
  量不出 28 倍这个差。
- **组填充率 85.8% 与 0.6% 的差距都是这一次语料的成绩。** 换一份冗余度不同的
  语料，上界与实际的差会变；但"迁移显著优于逐行写入"这个方向不会变，因为
  它来自机制（批量打包 vs 逐行封帧），不来自数据。
- **回滚会让库明显变大**：它把 5.64 GiB 明文写回列里（这个量是实测的），
  而且不 VACUUM 的话文件一字节都不缩。**回滚后的文件大小没有单独量**——
  它是 L2 降级，不是日常操作，量的价值不如把这次跑程的时间省下来。
