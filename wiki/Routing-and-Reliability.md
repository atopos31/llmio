# 调度与可靠性

本页说明一次请求如何选择上游，以及失败后如何处理。

![请求处理流程](images/request-flow.svg)

## 候选池的建立

请求进入网关后，LLMIO 按以下顺序建立候选池。

### 1. 查找模型

用请求体中的 `model` 查找同名模型。找不到时直接返回错误，并写一条错误日志。

### 2. 过滤关联

只保留满足以下条件的关联：

- 属于该模型。
- 状态为启用。
- 如果请求包含工具调用，关联勾选了「工具调用」。
- 如果请求包含结构化输出，关联勾选了「结构化输出」。
- 如果请求包含图片，关联勾选了「视觉」。

能力判断由请求体自动完成。客户端不需要显式声明。

### 3. 过滤提供商类型

按客户端协议选择可服务的上游类型：

| 客户端协议 | 可服务的上游类型 |
|---|---|
| OpenAI Chat Completions | `openai`，或可互转的 `anthropic` |
| OpenAI Responses | `openai-res` |
| Anthropic Messages | `anthropic`，或可互转的 `openai` |
| Gemini | `gemini` |

`openai-res` 与 `gemini` 不参与协议互转。模型列表可能合并显示 `openai` 与 `openai-res` 的模型；实际转发时，Chat Completions 请求应使用 `openai` 关联，Responses 请求应使用 `openai-res` 关联。

### 4. 优先匹配相同协议

如果模型的「优先匹配相同协议」开启（默认），且候选池中存在与客户端协议相同的提供商，则只保留这些提供商。没有同协议提供商时，才使用可互转的提供商。

关闭后，本协议与可互转协议的提供商一起参与权重调度。

### 5. 拆分主池与备用池

- 普通关联进入主池。
- 开启「备用关联」的关联进入备用池。
- 两池各自独立构建调度器。

备用池不参与日常轮询，只有主池在本请求内清空后才接管。

## 调度策略

### Lottery

按权重概率抽取。

- 每次取号时计算总权重，生成 `[0, 总权重)` 的随机数。
- 权重越大，命中概率越高。
- 关联失败时从池中删除。
- 收到 429 时，该关联权重减去当前值的 1/3，仍留在池中。整数除法会让权重小于 3 的关联基本不降权。

Lottery 适合把流量按比例分散到多家上游。

### Rotor

按权重从大到小排序，形成一个队列。

- 每次取队首。
- 成功时队首保持不动。
- 收到 429 时，把该关联移到队尾。
- 其他失败从队列中删除。

因此，只要队首关联持续成功，Rotor 就会一直使用它。它适合希望固定使用某一家上游、提高缓存命中率的场景，不适合按权重比例分散流量。需要按比例分配时使用 Lottery。

## 重试与超时

模型上的「重试次数限制」是一次请求最多尝试多少次，包含第一次。

- `MaxRetry = 1`：只尝试一次。
- `MaxRetry = 3`：最多尝试三次。
- 通过 API 创建模型时，`max_retry` 必须大于 0。

「超时时间」是整次请求的总时间预算。每次尝试、协议互转、参数自愈重发都受这个预算约束。流式请求等待上游响应头的时间为该值的三分之一，避免首包迟迟不来时一直占着连接。

重试过程中，每次失败都会写一条失败记录。最终成功或最终失败再写一条正式记录。因此日志页可能看到同一次客户端请求对应多条记录，它们的 TraceID 相同。

## 失败处理顺序

一次尝试失败后，LLMIO 按以下顺序处理。

### 400 / 422 且上游点名参数

适用条件：

- 状态码为 400 或 422。
- 响应体中的错误文本命中已知措辞，能提取出参数路径。
- 参数路径在实发请求体中存在。
- 参数不是保护字段，且本次请求没有删除过它。

满足条件时：

1. 从实发请求体中删除该参数。
2. 同一家上游立即重发。
3. 在 `bridge_notes` 中记录 `self_heal_dropped:参数名`。

限制：

- 每家上游在一次请求中最多删除 3 个参数。
- `model`、`messages`、`stream`、`tools`、`system`、`contents`、`input` 这些顶层字段不会被删除。
- 只处理 400 与 422。401、402、404、429、5xx 与参数存在性无关，直接走换家或降权。

参数自愈默认开启。策略保存在配置键 `self_heal_policy` 中，格式为：

```json
{"enabled": true, "max_drops": 3}
```

### 工具消息内容类型不匹配

部分老式上游只接受字符串形式的 `tool` 消息 `content`。当上游以类型错误拒绝块数组时，LLMIO 会把该消息压回纯文本：

- 保留文本块。
- 丢弃图片块。
- 记录 `dropped_tool_result_image`。
- 同一家上游最多降级一次。

这属于类型错误的单独降级路径，不占用参数删除预算。

### 429 Too Many Requests

- 不把关联移出候选池。
- Lottery：权重减去当前值的 1/3（整数除法；权重较小时可能不变）。
- Rotor：移到队尾。
- 继续消耗重试次数。

因此，如果所有主关联都持续返回 429，主池不会清空，备用池不会被启用；重试次数用尽后返回最后一次 429。

### 其他 4xx / 5xx / 网络错误

- 把关联移出本次候选池。
- 如果启用了熔断，计入一次失败。
- 换下一家。

客户端主动断开连接会被单独归因，不作为上游故障处理。

### 200 但响应体是错误

如果提供商配置了「响应体错误识别」，且响应为非流式，LLMIO 会读取响应体并匹配样本。命中任意样本时：

- 关闭响应体。
- 把关联移出候选池。
- 换下一家。

流式响应不会提前读取，因此不做这项检查。

### 协议互转失败

如果请求无法翻译成上游协议，LLMIO 把这次尝试视为失败，换下一家。转换层的记账会写入失败记录。

## 熔断

熔断是可选功能，按模型开启。开启后，调度器会被包一层熔断器。

状态机：

```text
Closed ──累计 5 次失败──▶ Open
Open ──60 秒冷却──▶ HalfOpen
HalfOpen ──连续 2 次成功──▶ Closed
HalfOpen ──任意一次失败──▶ Open
```

行为：

- `Closed`：正常参与调度。
- `Open`：该关联在冷却期内不参与取号。
- `HalfOpen`：允许探测请求。连续 2 次成功后恢复；任何一次失败都会重新进入 `Open`。
- 失败计数按关联 ID 记录在进程内，不跨进程共享，也不持久化。重启后状态清空。
- `Closed` 状态下的成功不会清零失败计数，因此进入 `Open` 的条件是「累计 5 次失败」，不要求连续。
- 收到 429 时，调度器会调用降权逻辑，熔断器也把它计入失败次数。

熔断适合隔离持续失败的上游。开启前请确认模型的关联数量足够，避免熔断后没有可用候选。

## 备用关联

备用关联是模型级别的后备方案。

适用场景：

- 主力上游价格低，但偶尔不可用。
- 希望保留一条平时不用、只在全部失败时接管的上游。

行为：

- 备用关联不参与日常轮询。
- 主池清空后，备用池接管。
- 接管后不回切主池。
- 日志的 `Backup` 字段标记本次响应是否来自备用池。

注意：429 只降权不移出主池，所以「主池全部 429」不会触发备用池。只有主池中的关联被移出（其他失败）后，备用池才会接管。

## 错误归因

失败记录会带阶段标记，便于判断问题发生在哪一段：

| 阶段 | 含义 |
|---|---|
| `upstream_request` | 构建请求、发起请求或等待上游响应头时失败。 |
| `response_stream` | 读取或解析上游响应流、向客户端转发时失败。 |
| `log_persist` | 日志自身写入数据库时失败。 |

客户端主动取消会标记为客户端断开，不计入上游故障。错误分类的统计口径见[用量分析](Analytics#错误)。

## 并发与顺序

- 每次请求独立建立调度器。一个请求内的失败、降权、删除不会影响其他请求。
- 熔断状态是共享的，按关联 ID 记录。
- 日志写入是异步的。响应返回后，日志可能稍后才出现在页面上。
- 协议转换的 `bridge_notes` 在每次换家时清空，只记录最终产出响应的那一家做过的改写。
